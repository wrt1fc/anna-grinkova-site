# Перенос на временный сервер

## Перед переносом

1. На сервере установить Node.js 24.15+, Git и, если нужен внешний доступ, Nginx с HTTPS. Выполнить `git clone`, `npm ci`, `npm test`.
2. Создать управляемый PostgreSQL у российского провайдера (тот же регион, что и сервер), отдельного пользователя базы с правами только на неё, доступ только из сети сервера. Строку подключения задать в `DATABASE_URL` (с `sslmode=require`). Схема создаётся при первом запуске (`server/schema.js`).
3. Секреты хранить вне репозитория, например в переменных окружения сервиса. За основу взять [`deploy/env.example`](../deploy/env.example). Для `AUTH_CODE_SECRET` сгенерировать случайные 32+ байта; не использовать образец как секрет. Не выводить значения в логи. Выдать ключу почты минимальные права и задать явный `MAIL_DAILY_LIMIT`.
4. Приложение слушает `127.0.0.1:3000`. Внешний HTTPS и ограничение API настроить по [`deploy/nginx.example.conf`](../deploy/nginx.example.conf). Подставить настоящий домен и сертификаты; закрыть прямой доступ к порту Node. Проверка готовности: `GET /api/health` → `200 {"status":"ok"}`.
5. Локальный Ollama и модель ставятся отдельно. `FORECAST_LOCAL_MODEL` включать только после проверки серии ответов по [`forecast-voice.md`](forecast-voice.md). Без модели остаётся расчётный текст. Платную облачную модель сейчас не подключать.

## Резервная копия и восстановление

Основная защита — резервные копии провайдера с восстановлением на любую минуту (point-in-time recovery): включить в панели, срок хранения не меньше 7 дней. Дополнительно раз в сутки — своя копия в зашифрованное хранилище S3 того же провайдера:

```bash
DATABASE_URL=postgres://… node scripts/db.js backup /var/backups/anna/anna-$(date +%F).dump
DATABASE_URL=postgres://…/anna_restore_test node scripts/db.js restore /var/backups/anna/anna-2026-10-08.dump
```

Скрипт вызывает `pg_dump`/`pg_restore` (нужен пакет клиента PostgreSQL), пароль передаёт через переменные окружения, а не в командной строке, и не перезаписывает существующий файл копии. Восстанавливать сначала в отдельную проверочную базу, убедиться, что аккаунты, профили и заказы читаются, и только потом переключать `DATABASE_URL`. Раз в месяц проверять восстановление.

## Наблюдение и лимиты

- Проверять `/api/health` локальным мониторингом. Сервис отвечает `503`, если база недоступна; Nginx в таком случае также покажет ошибку шлюза. Логи процесса хранить у менеджера сервиса, без тел запросов, почтовых кодов, токенов и профилей рождения.
- Встроенные лимиты API действуют в одном процессе; Nginx ограничивает внешние обращения до передачи Node. Включите `TRUST_PROXY=1` и передавайте `X-Real-IP` (см. пример Nginx), иначе Node видит всех посетителей как `127.0.0.1` и делит между ними один лимит. `MAIL_DAILY_LIMIT=0` отключает платную отправку писем по умолчанию. Для запуска регистрации нужна осознанно заданная квота и рабочая почта.
- Установить системные лимиты на диск и память, уведомления об ошибках, контроль свободного места и доступности почтового провайдера. Еженедельно проверять резервное копирование; перед обновлением кода делать новую копию.
- CI запускает тесты и аудит зависимостей. Прежде чем обновлять библиотеку расчётов, сравнить эталонные положения планет и дневные события.

## Источники данных

Каталог городов взят из GeoNames `cities15000`, лицензия [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/), источник: [GeoNames export](https://download.geonames.org/export/dump/). В репозитории включена сохранённая выборка 23 050 городов из более старого зеркала; для актуализации скачать официальный `cities15000.zip`, распаковать и выполнить `python scripts/build-city-catalog.py cities15000.txt`. Редкие населённые пункты можно ввести вручную. Исторические часовые пояса зависят от актуальности базы IANA в Node и требуют ручной проверки для спорных дат.

Сверка с Sotis использует публичный веб-интерфейс без официального API. Она не должна быть единственным источником прогноза. На другой машине проверить доступность и условия использования сервиса до коммерческого запуска.
