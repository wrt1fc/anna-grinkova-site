# База данных

PostgreSQL. Сервер подключается по `DATABASE_URL`:

| Где | `DATABASE_URL` | Что это |
| --- | --- | --- |
| Боевой сервер | `postgres://…?sslmode=require` | управляемый PostgreSQL у российского провайдера, в том же регионе, что и сайт |
| Разработка | не задан → `pglite:./data/pglite` | PGlite — тот же PostgreSQL, собранный в WebAssembly, работает внутри Node без установки |
| Тесты | `pglite:memory` | чистая база в памяти на каждый тест; отдельный тест гоняет код через драйвер `pg` по сетевому протоколу |

Код: `server/db.js` (подключение, пул, транзакции), `server/schema.js` (миграции), `server/store.js`, `store-extras.js`, `store-billing.js` (запросы). Все запросы параметризованы (`$1`, `$2`…). Деньги хранятся целыми числами в минимальных единицах (копейки, центы), время — миллисекунды Unix в `BIGINT`.

## Миграции

Схема — пронумерованные миграции в `server/schema.js`. Каждая выполняется один раз, в транзакции, номер записывается в `schema_migrations`. Перед применением берётся advisory-блокировка, поэтому два одновременно стартующих сервера не применят миграцию дважды. Новую миграцию добавлять **в конец списка**; уже применённые в бою не менять.

## Одновременные запросы

- Изменения тарифа, профилей близких и обработка оплаты идут в транзакции с блокировкой строки пользователя (`SELECT … FOR UPDATE`). Две параллельные вкладки не превысят лимит людей на тарифе, а повторные уведомления провайдера не продлят тариф дважды. Это проверяет тест с параллельными запросами.
- Код подтверждения блокируется на время проверки, поэтому один код нельзя использовать дважды.
- Дневные лимиты и повторная отправка кода проверяются одним атомарным `INSERT … ON CONFLICT … WHERE`.

## Таблицы

| Таблица | Что хранит | Сколько живёт |
| --- | --- | --- |
| `users` | почта, хэш пароля (scrypt), подтверждение почты, имя для обращения, тариф и его окончание, согласие на хранение чата, сохранённый способ автоплатежа (`autorenew_method_id`, провайдер и валюта) | пока есть аккаунт |
| `sessions` | хэш токена сессии и срок | 30 дней, удаляются при выходе |
| `auth_challenges` | коды подтверждения почты и сброса пароля (только хэши), попытки | 10 минут |
| `birth_profiles` | данные рождения владельца: дата, время, место, координаты, часовой пояс, момент UTC | пока есть аккаунт |
| `chart_profiles` | близкие на партнёрском и семейном тарифах: связь, имя, те же поля рождения | пока есть аккаунт; при удалении профиля удаляется и его переписка |
| `chat_messages` | переписка в чате, **только при согласии** | 180 дней и не больше 500 сообщений; отзыв согласия удаляет всё |
| `daily_quotas` | счётчики сообщений и писем за день | обновляются ежедневно |
| `orders` | заказы: тариф, срок, сумма и валюта, статус (`pending`, `paid`, `canceled`, `failed`, `refunded`), провайдер, номер платежа у провайдера, числовой номер счёта `invoice_no` из последовательности (для Robokassa), автопродление | не удаляются: это учётные записи о платежах |
| `payment_events` | какие уведомления провайдера уже обработаны | можно чистить старше года |
| `metrics_daily` | обезличенные счётчики: просмотры, сообщения, ошибки, время ответа | бессрочно, персональных данных нет |
| `visitors_daily` | хэш посетителя за текущий день для подсчёта уникальных | удаляется на следующий день |
| `schema_migrations` | номера применённых миграций | всегда |

Пароли, коды и токены сессий в базе только в виде хэшей. Дата и место рождения и почта никогда не передаются модели: в чат уходит только рассчитанная карта.

## Персональные данные: Россия и зарубеж

- **152-ФЗ.** Данные граждан РФ должны первично записываться и храниться в базе на территории России. Поэтому одна общая база — в России, для всех пользователей. Отдельная зарубежная база не нужна и только разнесла бы аккаунты, оплаты и тарифы.
- **Зарубежные пользователи.** Хранить их данные в России можно. Для жителей ЕС действует GDPR, а Россия для ЕС — страна без «адекватной защиты». Поэтому нужны политика конфиденциальности с разделом GDPR и явное согласие на обработку в России при регистрации. Текст готовит юрист.
- Персональные данные: почта, имя, данные рождения (свои и близких), переписка. Для переписки — отдельное согласие (`chat_history_consent_at`); для данных близких пользователь подтверждает, что вправе их передать (оферта и политика).
- Удаление аккаунта (`DELETE /api/me` с паролем): стираются `birth_profiles`, `chart_profiles`, `chat_messages`, `sessions`, коды; если заказов нет — удаляется и сам пользователь, иначе он обезличивается (почта → `deleted-<id>@deleted.invalid`, без пароля, имени и согласий). Заказы остаются (`ON DELETE RESTRICT`): платёжные записи нужны для бухгалтерии и чеков. Выгрузка своих данных — `GET /api/me/export`.
- Согласие на обработку данных при регистрации хранится с датой и версией политики (`users.privacy_consent_at`, `privacy_policy_version`; версия — в `config/legal.json`, менять при каждом изменении текста политики).
- Ежедневная очистка (`scripts/daily.js`): просроченные сессии и коды, счётчики старше недели, обработанные уведомления оплат старше года, переписка старше 180 дней у всех пользователей.

## Сервер базы и резервные копии

- Управляемый PostgreSQL у того же российского провайдера, что и сервер сайта, доступ только из его сети, TLS (`sslmode=require`, лучше `verify-full` с сертификатом провайдера), отдельный пользователь с правами только на эту базу.
- Основная защита — копии провайдера с восстановлением на любую минуту (PITR), срок хранения от 7 дней.
- Дополнительно раз в сутки — `node scripts/db.js backup <файл.dump>` (pg_dump) в зашифрованное хранилище S3, 14 дневных и 8 недельных копий. Раз в месяц — проверочное восстановление в отдельную базу (`scripts/db.js restore`).
- Пул соединений — `DATABASE_POOL_SIZE` (по умолчанию 10 на процесс). Для второго сервера приложения ничего менять не нужно: оба подключаются к одной базе.
- Когда понадобится отказоустойчивость — реплика в другой зоне доступности у того же провайдера.
