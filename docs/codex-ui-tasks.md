# Задачи интерфейса для Codex

Бэкенд и модель ведёт другая сессия; здесь описано, что нужно нарисовать поверх уже готовых API. Стиль — текущий: тёмный тёплый фон, бронза и золото, Wix Madefor Display / Roboto / Playfair Display Italic. Без слов «ИИ», «нейросеть», «модель» в интерфейсе. Все ответы API — JSON, ошибки содержат `error` и человекочитаемое `message`, которое можно показывать как есть.

## 1. Согласие на хранение истории чата

Без согласия переписка живёт только в памяти страницы. С согласием сервер хранит последние сообщения до 180 дней.

- Где: в кабинете (блок «Безопасность» или отдельный «Чат») и коротким баннером над полем ввода при первом входе в чат, пока пользователь не ответил.
- Текст (черновик, утвердить с юристом): «Сохранять переписку в чате, чтобы вернуться к ней позже. Храним до 180 дней, удалить можно в любой момент». Две кнопки: «Сохранять» и «Не сохранять».
- API: `PUT /api/chat/consent` с `{ "consent": true | false }`. При `false` сервер сразу удаляет сохранённую историю — предупредите об этом в подтверждении.
- Состояние: `GET /api/chat/history` → `{ consent, messages }`.
- Согласие обязательно по 152-ФЗ: галочка не стоит по умолчанию, отказ не ограничивает чат.

## 2. История переписки

- При открытии чата, если `consent: true`, показать сообщения из `GET /api/chat/history` под приветствием (роль `user` / `assistant`, поле `content`). Для сообщений о близком есть `profileId`.
- Кнопка «Очистить историю» в кабинете: `DELETE /api/chat/history` с подтверждением.
- Восстановленные ответы не подписаны, поэтому в `chatHistory` для продолжения разговора их не добавлять — только показывать.

## 3. Тарифы и близкие люди

Тарифы: «Индивидуальный» (1 человек), «Партнёрский» (вы + партнёр), «Семейный» (вы + ещё двое). Пока оплата не подключена, тариф назначает оператор (`node scripts/set-plan.js <email> <individual|partner|family>`).

- `GET /api/profiles` → `{ plan: { id, label, maxPeople, dailyChatMessages, relations }, self, profiles: [{ id, relation, label, birthDate, birthTime, birthPlace, …, locked }], relationLabels }`.
- `POST /api/profiles` — `{ relation, label, birthDate, birthTime, birthCityId | birthPlace + координаты + birthTimeZone }`, поля как у своего профиля. `relation` — из `plan.relations`. Ошибка `plan_limit` (403) — показать сообщение и ссылку на смену тарифа.
- `PUT /api/profiles/:id`, `DELETE /api/profiles/:id`.
- `label` — до 40 букв, цифр, пробелов (например «Сергей», «Мама»).
- В кабинете: блок «Близкие» со списком карточек и кнопкой «Добавить человека». Форма — та же, что для своих данных рождения, плюс выбор связи (`relationLabels`) и имя. Профили с `locked: true` показывать приглушёнными с подписью «Недоступно на текущем тарифе».
- Счётчик «2 из 3 человек» по `plan.maxPeople`.

## 4. Переключатель «О ком вопрос» в чате

Как «Моя карта / Переключить» у Селены.

- В шапке панели чата: чип с именем текущего профиля («Я», «Сергей»…), по нажатию — список профилей из `GET /api/profiles` (заблокированные недоступны).
- Чат уже читает выбор из функции `window.chatSelectedProfileId()`: она должна вернуть `id` профиля или `null` для себя. Достаточно определить эту функцию.
- В ответе `context.subject` (`{ relation, label }`) — чат уже подписывает ответ «Сергей · Личный расчёт · …».

## 5. Лимиты и состояния чата

- `chat_daily_limit` (429): «Сообщения на сегодня по тарифу закончились» — показать с предложением сменить тариф.
- `chat_busy` (503) и `chat_rate_limited` (429): уже выводятся как ошибка с кнопкой «Повторить».
- `chat_in_progress` (429): у этого пользователя уже идёт ответ. Кнопку отправки и так блокирует чат, но при двух открытых вкладках это сообщение можно показать как подсказку, а не как ошибку.
- Кризисный ответ приходит с `crisis: true` — показать его без кнопки «Скопировать» и без подписи расчёта, можно выделить мягкой рамкой. Номера телефонов сделать ссылками `tel:`.

## 6. Поток ответа

Уже работает: `POST /api/chat` с `Accept: text/event-stream` отдаёт события `delta`, `done`, `error`. Если правите `prototype/chat.js`, не ломайте `readEvents` и замену текста на `done` (так ответ, остановленный проверкой, заменяется безопасным текстом).

## 7. Оплата тарифов: Россия и зарубеж

API готов, нужен интерфейс. Цены пока черновые (`config/products.json`), их утверждает Анна.

- Тарифы и способы оплаты: `GET /api/billing/products` → `{ products: [{ id, label, plan, planLabel, maxPeople, periodDays, prices: { RUB, USD, EUR }, oncePerUser, autoRenewable }], regions: [{ id: "ru" | "intl", label, currencies, available }] }`.
- Экран тарифов (кабинет и ссылка из сообщения `chat_daily_limit`): карточки «Тест-драйв», «Индивидуальный», «Партнёрский», «Семейный»; на карточке — сколько человек, сообщений в день и срок. Рекомендуемый тариф выделить.
- Над карточками — переключатель способа оплаты из `regions` (только `available: true`): «Карта российского банка, СБП, SberPay» — цена в ₽; «Карта иностранного банка» — выбор USD/EUR и цена в этой валюте. Если доступен только один способ, переключатель не показывать.
- Чекбокс «Продлевать автоматически каждые 30 дней» — только у `autoRenewable`, **не отмечен по умолчанию**. Рядом короткий текст: «Спишем ту же сумму с этой карты за день до окончания. Отключить можно в кабинете в любой момент». Это согласие на автоплатёж — без явной галочки продление не включается.
- Кнопка «Оплатить»: `POST /api/billing/checkout` с `{ productId, region, currency, autoRenew }` → `{ orderId, confirmationUrl }`; перейти на `confirmationUrl` (страница ЮKassa или Robokassa). Ошибки: `already_used` (409, тест-драйв уже был), `billing_unavailable` (503), `invalid_currency` (400) — показывать `message`.
- Возврат: провайдер вернёт на `/kabinet?payment=<orderId>`. Показать «Проверяем оплату…» и опрашивать `GET /api/billing/orders/:id` раз в 2 секунды до 60 секунд, пока `status` не станет `paid` (успех, обновить тариф), `canceled`/`failed` (не прошла, кнопка «Попробовать ещё раз»). Если за минуту ответа нет — «Оплата ещё обрабатывается, тариф включится автоматически». Сам переход по ссылке доступ не даёт: тариф включает только подтверждение от провайдера.
- Блок «Подписка» в кабинете: `GET /api/billing/subscription` → `{ plan: { id, label, expiresAt, autoRenew }, orders }`. Показать «Семейный до 7 ноября», статус автопродления и кнопку «Отключить автопродление» → `DELETE /api/billing/autorenew`. Ниже — история платежей (`amount`, `currency`, дата, статус).
- Под кнопкой оплаты — ссылки на оферту и политику обработки персональных данных (документы готовит юрист; пока заглушки).

## 8. Приложение на телефоне (iPhone и Android)

Сайт уже устанавливается как приложение: есть манифест, иконки и `sw.js` (подключает `prototype/pwa.js`, его не трогать). Нужен интерфейс:

- Кнопка «Установить приложение» в кабинете и в мобильном меню. Android/Chrome: показывать, когда `document.documentElement.dataset.installable === 'true'`; по нажатию вызвать `window.annaInstallPrompt.prompt()`. iPhone (Safari): подсказка «Нажмите „Поделиться“ → „На экран «Домой»“» с иконкой. В установленном приложении (`dataset.standalone === 'true'`) кнопку скрыть.
- Безопасные зоны: `viewport-fit=cover` уже включён, поэтому шапке нужен отступ `env(safe-area-inset-top)`, боковым краям — `env(safe-area-inset-left/right)`; нижнее меню уже учитывает `safe-area-inset-bottom`. Проверить на iPhone с «чёлкой» в портретной и альбомной ориентации.
- В режиме приложения нет адресной строки и кнопки «Назад» браузера на iOS: на внутренних экранах (карта дня, неделя, чат, кабинет) нужна своя кнопка «Назад».
- Поле ввода чата: на iOS клавиатура не должна перекрывать поле (использовать `visualViewport` или `100dvh`), размер шрифта в полях не меньше 16px, иначе Safari увеличивает страницу.
- Касания: цели не меньше 44×44, без зависимости от наведения.

## 9. Согласие при регистрации, юридические документы, удаление аккаунта

Без этого сайт нельзя запускать (152-ФЗ); на боевом сервере регистрация без согласия отклоняется.

- Форма регистрации: обязательная галочка, **не отмеченная по умолчанию**: «Я соглашаюсь на обработку персональных данных и принимаю [политику обработки персональных данных] и [пользовательское соглашение]». Без неё кнопка «Создать аккаунт» неактивна. В запрос `POST /api/auth/register` добавить `privacyConsent: true`. Ошибка `consent_required` (400) — показать `message`.
- Отдельной строкой для зарубежных пользователей (текст согласует юрист): согласие на хранение данных на серверах в России.
- Подвал сайта: ссылки «Политика обработки персональных данных», «Пользовательское соглашение», «Публичная оферта» (страницы `#privacy`, `#terms`, `#offer`; тексты готовит юрист, пока заглушки «Документ готовится»).
- Кабинет, блок «Данные и аккаунт»:
  - «Скачать мои данные» → `GET /api/me/export` (файл JSON).
  - «Удалить аккаунт» → подтверждение с паролем → `DELETE /api/me` с `{ password }`. Ошибка `invalid_password` (403). После успеха — выход и сообщение «Аккаунт удалён». В тексте подтверждения: «Профиль, данные рождения, близкие и переписка удаляются сразу. Записи об оплатах хранятся обезличенно, как требует закон о бухгалтерском учёте».
- Регистрация и сброс пароля: при `mail_limit` (429) показать `message` как есть. Сброс пароля всегда отвечает «Если аккаунт существует, код отправлен на почту» — так и показывать, не утверждать, что письмо точно отправлено.

## 10. Адреса страниц и поисковики

Разделы теперь открываются по настоящим адресам: `/`, `/karta-dnya`, `/prognoz-na-nedelyu`, `/chat`, `/kabinet` (старые ссылки `#day` и т. п. перенаправляются). Сервер по каждому адресу подставляет свой title, description, canonical и показывает в HTML только этот раздел.

- Внутренние ссылки — обычные `<a href="/karta-dnya">`, не `#day`. Переход без перезагрузки делает `app.js`; из других скриптов — `window.navigateTo('account')`.
- Атрибут `data-page="…"` у разделов не убирать: по нему сервер показывает нужный раздел.
- Новая страница (например, документы `/privacy`, `/terms`, `/offer` из §9 или статьи) — добавить адрес в `config/seo.json` (title до 60 символов, description 140–160) и в `ROUTE_PATHS` в `app.js`.
- Один `<h1>` на раздел, с ключевым словом: «Карта дня таро», «Прогноз на неделю», «Чат с Анной». Подзаголовки — `<h2>`, по смыслу, не для оформления.
- Картинкам со смыслом — осмысленный `alt` (портрет: «Анна Гринькова, астропсихолог»), декоративным — `alt=""`.
- Возврат с оплаты теперь на `/kabinet?payment=<orderId>`.

## 11. Расклад по запросу: колода, запрос, номер карты, трактовка

**Статус (21.10.2026): сделано по макету Figma** — `prototype/reading.css`, `prototype/reading.js`, раздел `#route-reading` в `index.html`, адрес `/rasklad` (`config/seo.json`, `ROUTE_PATHS` в `app.js`), ссылка «Расклад по запросу» на странице дня. Ниже — исходное описание, по нему проверять правки.

Сервер готов (`POST /api/tarot/reading`, свои пять карт на каждого вошедшего). Нужно нарисовать путь на странице `/karta-dnya`. Без слов «ИИ», «нейросеть», «модель» в интерфейсе.

**Путь пользователя:**
1. Колода: короткая анимация, карты веером или стопкой (рубашка — `assets/card-back.svg`).
2. Показываются **5 закрытых карт**, под каждой номер 1–5. Карта не открыта, пока пользователь не назвал номер.
3. Поле «Ваш вопрос» (до 300 символов, счётчик остатка, `maxlength="300"`, шрифт ≥ 16 px). Подсказка-пример: «Что мне важно понять о работе в ближайшее время?».
4. Выбор номера карты 1–5 (кнопки с номерами, не набор цифр с клавиатуры) и кнопка «Открыть карту».
5. Карта переворачивается (имя и номер из ответа), под ней появляется трактовка. Ответ приходит потоком, как в чате (§6): `Accept: text/event-stream`, события `delta`, `done`, `error`.
6. Под трактовкой — текст: «Расклад — повод для размышления, а не предсказание. Не заменяет консультацию специалиста».

**Кто что видит:**
- **Гость:** общий набор карт дня, карту можно открыть и увидеть название (`GET /api/forecast/card?draw=N`). Ввод запроса и трактовка закрыты: вместо них блок «Трактовка по вашему вопросу — после регистрации» и кнопка `data-open-signup`. `POST /api/tarot/reading` без входа возвращает 401 `login_required`.
- **Вошедший пользователь:** его собственные 5 карт на день. Набор не меняется при обновлении страницы, завтра будет другой. Карту по номеру `N` сервер берёт той же функцией, что рисует колоду, поэтому открытая карта всегда совпадает с трактовкой.

**API:**
- Карта номера: `GET /api/forecast/card?draw=N`, где `N` от 0 до 4 (номер на экране минус 1) → `{ date, tarot: { number, name } }`. Уже работает для вошедших без данных рождения.
- Трактовка: `POST /api/tarot/reading` с `{ "question": "…", "draw": N }`, `N` — целое от 0 до 4 (**число, не строка**). Ответ: `{ answer, filtered, card: { number, name, position } }` (`position` — номер на экране, 1–5). Потоковый вариант: тот же запрос с `Accept: text/event-stream`, итоговый `done` содержит то же самое.
- Ошибки (показывать `message` как есть): `login_required` (401), `invalid_tarot_reading` (400, вопрос пуст или длиннее 300), `tarot_daily_limit` (429, лимит на сегодня исчерпан: предложить сменить тариф), `chat_rate_limited` (429), `chat_in_progress` (429, дождаться ответа), `chat_busy` (503), `tarot_unavailable` (503, кнопка «Повторить»: попытка при ошибке не списывается).
- Кризисный вопрос возвращает `{ crisis: true, answer }`: показать без трактовки и без подписи карты, номера телефонов ссылками `tel:`, как в чате (§5).
- Лимит раскладов в день — в `GET /api/plan` и `GET /api/profiles`: `plan.dailyTarotReadings` (бесплатный 1, индивидуальный 3, партнёрский 5, семейный 8; числа черновые, утверждает Анна). Показать «Осталось N на сегодня» нельзя, остаток API пока не отдаёт: для этого нужно будет дописать сервер.
- Вопросы раскладов в историю чата не сохраняются.

**Состояния:** загрузка трактовки (кнопка отключена, «Открываем карту…»), ошибка с повтором, лимит исчерпан, карта открыта (можно открыть ещё одну для нового вопроса, пока есть лимит). На 375 px: пять карт не вылезают за экран (две строки или карусель), цели касания ≥ 44×44, фокус виден, всё работает с клавиатуры, `prefers-reduced-motion` — без анимации колоды.
