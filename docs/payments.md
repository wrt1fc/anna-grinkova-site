# Подключение оплаты

Первый сценарий — разовый доступ на 24 часа к прогнозу дня и на 7 дней к прогнозам дня и недели. Это не автопродление. Цена пока не утверждена и намеренно не указана в интерфейсе.

## Возможные сервисы

| Сервис | Что уже подтверждено в документации | Для выбора |
|---|---|---|
| [ЮKassa](https://yookassa.ru/developers/using-api/webhooks) | API и уведомления о статусе платежа и возврата | Проверить условия договора и тариф для бизнеса Анны |
| [CloudPayments](https://developers.cloudpayments.ru/) | API, уведомления Pay/Refund, рекуррентные платежи и проверка HMAC | Подходит, если позже понадобится автопродление; проверить тариф и договор |
| [Т-Банк Эквайринг](https://developer.tbank.ru/eacq/intro/developer/notification) | API и HTTP(S)-уведомления о статусах | Проверить условия подключения и способы оплаты для бизнеса Анны |

Рекомендация для первого подключения: выбрать сервис после сравнения договора, комиссии, чеков и доступных способов оплаты для юридического статуса продавца. Текущая модель заказа не привязана к конкретному провайдеру.

## Контракт будущей интеграции

1. Сервер получает выбранный план, берёт цену из собственной конфигурации и создаёт заказ `pending`.
2. Сервер создаёт платёж у провайдера и отдаёт клиенту только адрес платёжной страницы.
3. Возврат пользователя с платёжной страницы не выдаёт доступ. Сервер проверяет подписанное уведомление или запрашивает статус у провайдера, сверяет заказ, сумму и валюту, затем вызывает `confirmPayment`.
4. Повторное уведомление не продлевает доступ. Подтверждённый возврат вызывает `refundPayment` и закрывает права.
5. Только после этого сервер разрешает запрос персонального прогноза. Проверка стоит в API, не в браузере.

Для подключения понадобятся: выбранный сервис и аккаунт продавца, утверждённые цены, тестовые и рабочие ключи, публичный HTTPS-адрес для уведомлений и сведения для оформления чеков. Секреты держать только на сервере, вне Git.
