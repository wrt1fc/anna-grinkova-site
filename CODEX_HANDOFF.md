# Передача проекта Codex на другой компьютер

Этот файл — точка входа для продолжения работы на временном сервере. Актуальная работа находится в ветке `feat/account-payments`, [PR #1](https://github.com/wrt1fc/anna-grinkova-site/pull/1). Ветка может быть ещё не объединена с `main`; после клонирования явно переключитесь на неё. Утверждённый дизайн сайта сохраняется.

## Первый запуск на другом ПК

Нужен Node.js **24.15+** и Git. На Windows в PowerShell:

```powershell
git clone https://github.com/wrt1fc/anna-grinkova-site.git
cd anna-grinkova-site
git switch feat/account-payments
npm ci
npm test
npm start
```

Открыть `http://127.0.0.1:3000`, проверить `http://127.0.0.1:3000/api/health` и страницу «Карта дня». Если порт занят, задать `PORT` перед `npm start`. База по умолчанию создаётся в `data/site.sqlite`; каталог исключён из Git. Свободный запуск без почтового ключа показывает сайт, но новая регистрация отвечает `503`, поскольку код подтверждения отправить нечем.

## Что уже работает

- Сайт на обычных HTML/CSS/JavaScript, сервер Node.js, SQLite. Личный кабинет: регистрация и восстановление пароля по коду из письма, сессии, профиль рождения.
- `GET /api/cities?q=Москва` ищет город в локальном каталоге GeoNames. Профиль сохраняет выбранный город, координаты, IANA-зону и рассчитанный UTC-момент рождения. Для редкого места есть ручной ввод. Старое свободное название места без координат не даёт персональный прогноз.
- `GET /api/forecast/day`: гостю — общий прогноз; вошедшему пользователю с разрешённым профилем — персональный. Планетные положения, переходы Луны и аспекты считает Astronomy Engine. Таро выбирается цифровым воспроизводимым способом; для аккаунта выбор отдельный. Общий кэш не содержит личных данных.
- По умолчанию первый запрос дня сверяет долготы Солнца и Луны с публичным интерфейсом Sotis. На него не отправляются данные рождения пользователя. Интерфейс Sotis не документирован как API: при сбое расчёт остаётся локальным. `SOTIS_VERIFY=0` выключает сверку.
- Локальный Ollama/Qwen может переформулировать **общий** текст после проверки фактов. Персональный текст пока строится правилами. Модель не входит в Git и не была проверена на этом ПК.
- В `config/forecast-style.json`, `docs/forecast-voice.md` и `docs/forecast-style-examples.md` лежат предварительные редакционные настройки по полному 68-минутному эфиру. Это не обученные веса модели и не авторизованные тексты Анны.

## Секреты, почта и данные

Настройки перечислены в `deploy/env.example`; настоящий файл с секретами храните **вне репозитория**. Для рабочего запуска нужны постоянный случайный `AUTH_CODE_SECRET` длиной минимум 32 символа, `NODE_ENV=production`, HTTPS, приватный `DATA_PATH` и права на каталог базы. Почта реализована через Unisender Go, но аккаунт, ключ и подтверждённый адрес отправителя должен предоставить владелец проекта. `MAIL_DAILY_LIMIT=0` по умолчанию выключает отправку; при подключении задайте явную суточную квоту.

Не переносите через Git `data/`, `.env`, резервные копии, ключи, `record.ogg` и сырые расшифровки. Для переноса существующих аккаунтов используйте `node scripts/db.js backup <исходная.sqlite> <новая-копия.sqlite>` и передайте копию защищённым каналом. `restore` создаёт **новый** файл и проверяет целостность. Подробные шаги, включая Nginx и мониторинг, находятся в `docs/server-transfer.md`.

## Подключение локальной модели

Установите Ollama и выбранную локальную модель на новом ПК. В проекте предусмотрена `qwen3:4b`: после её загрузки задайте `FORECAST_LOCAL_MODEL=qwen3:4b` и перезапустите сайт. Сервер обращается к `127.0.0.1:11434`. Проверьте десять разных дат по критериям `docs/forecast-voice.md`: численные факты сохранены, совет конкретен, нет выдуманных аспектов и личных сведений. При ошибке модели приложение возвращает редакционный текст. Публикацию текстов от имени Анны согласуйте с ней. Специализированную «астрологическую» модель и цепочку перевода с Qwen в код не добавляли: расчёт уже делает проверяемая библиотека, а оценка качества такой цепочки ещё не проведена.

## Следующие задачи для Codex

1. Проверить чистую установку и работу на конкретном ПК: Node, свободное место, права базы, локальный порт, HTTPS и лимиты прокси. Не открывать Node напрямую в интернет. При необходимости настроить менеджер процесса и регулярные зашифрованные резервные копии.
2. После получения почтового аккаунта подключить ключи и домен, проверить регистрацию и восстановление пароля настоящими письмами. Проверить фактические расходы и квоту провайдера.
3. Обновить каталог GeoNames из официального экспорта по инструкции `docs/server-transfer.md` и проверить исторические зоны для спорных мест и дат.
4. Установить и оценить локальную модель, собрать одобренные Анной примеры, затем улучшать редакционный слой дневного прогноза. Не поручать LLM вычисление положений планет.
5. Прогноз на неделю делать после принятия качества дневного. Оплату не подключать, пока владелец не выберет провайдера, цены и правила доступа (`docs/payments.md`).

Перед каждым коммитом запускать `npm test` и `npm audit --omit=dev --audit-level=high`; изменения отправлять в Git. Последняя проверка перед этим файлом: 41 тест прошёл локально и в CI, из чистой копии работали `/`, `/api/health`, `/api/cities` и `/api/forecast/day`.
